\section{Descripción del caso}

SoundCloud arrancó con un monolito Ruby on Rails llamado «Mothership». Allí convivían la API pública y la aplicación web~\cite{calcado2014monolith}. En 2014 los usuarios subían unas 12 horas de contenido por minuto y miles de aplicaciones de terceros usaban la API~\cite{calcado2014monolith}. El equipo dejó de añadir funciones al monolito. Las nuevas se construyeron como microservicios y el código existente se extraía solo al refactorizarlo~\cite{calcado2014monolith}. La migración duró ocho años~\cite{obrien2022strangler}. El «Strangler», creado en 2014, avanzó poco durante seis; el trabajo serio para retirarlo empezó en enero de 2020~\cite{obrien2022strangler}.

\section{Por qué SoundCloud eligió microservicios y qué tenía antes}

Todo vivía en un solo código. La aplicación Rails, con MRI, memcached y MySQL, servía la API pública y la web. Desde Next SoundCloud, en 2012, la API pública era la interfaz principal y los clientes propios se construyeron sobre ella~\cite{calcado2014monolith}. El equipo sentía que solo parchaba el sistema sin resolver el problema de fondo de escalabilidad. Debía reaccionar también a la actividad de los usuarios, y consultar periódicamente al servidor (polling) no era viable a esa escala~\cite{calcado2014monolith}. Los servicios nuevos no leen la base de datos del monolito. Usan su API pública, porque la base es una interfaz no publicada y cambiar tablas compartidas causa problemas~\cite{calcado2014monolith}.
