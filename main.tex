\section{Descripción del caso}

SoundCloud arrancó con un monolito Ruby on Rails llamado «Mothership». Allí convivían la API pública y la aplicación web~\cite{calcado2014monolith}. En 2014 los usuarios subían unas 12 horas de contenido por minuto y miles de aplicaciones de terceros usaban la API~\cite{calcado2014monolith}. El equipo dejó de añadir funciones al monolito. Las nuevas se construyeron como microservicios y el código existente se extraía solo al refactorizarlo~\cite{calcado2014monolith}. La migración duró ocho años~\cite{obrien2022strangler}. El «Strangler», creado en 2014, avanzó poco durante seis; el trabajo serio para retirarlo empezó en enero de 2020~\cite{obrien2022strangler}.

\section{Por qué SoundCloud eligió microservicios y qué tenía antes}

Todo vivía en un solo código. La aplicación Rails, con MRI, memcached y MySQL, servía la API pública y la web. Desde Next SoundCloud, en 2012, la API pública era la interfaz principal y los clientes propios se construyeron sobre ella~\cite{calcado2014monolith}. El equipo sentía que solo parchaba el sistema sin resolver el problema de fondo de escalabilidad. Debía reaccionar también a la actividad de los usuarios, y consultar periódicamente al servidor (polling) no era viable a esa escala~\cite{calcado2014monolith}. Los servicios nuevos no leen la base de datos del monolito. Usan su API pública, porque la base es una interfaz no publicada y cambiar tablas compartidas causa problemas~\cite{calcado2014monolith}.

\section{Beneficios obtenidos}

Las fuentes no publican mediciones de latencia, costes ni incidentes. Los beneficios que describen son cualitativos. Calçado señala ciclos de retroalimentación mucho más cortos para llevar funciones a producción, y da como ejemplo el nuevo sistema de estadísticas~\cite{calcado2014monolith}. Dejar de añadir código al monolito evitó refactorizaciones masivas~\cite{calcado2014monolith}. Al cierre de la migración, el código de la API pública salió del monolito y el Strangler pasó a ser un BFF (backend for frontend, servicio que adapta la API a cada cliente) completo en Scala, un lenguaje que la mayoría de los ingenieros puede aprender a tocar~\cite{obrien2022strangler}.

\section{Desafíos encontrados y cómo se resolvieron}

Las fuentes describen tres problemas. El primero fue evitar una refactorización «big-bang»: SoundCloud dejó de añadir funciones al monolito y extrajo código solo al refactorizar~\cite{calcado2014monolith}. El segundo, la extracción no avanzaba. Cada entidad tardaba varios meses, dependía de todos los equipos y algunos servicios seguían leyendo la base del monolito. Repartieron el cambio de los puntos de llamada, redefinieron «terminado», fijaron normas de integración y midieron el avance con monitoreo~\cite{stuart2016monolith}. El tercero, el Strangler quedó sin mantenimiento, con rutas duplicadas, pérdida de conocimiento y un Rails obsoleto expuesto. Portaron todos los endpoints y eliminaron el código de la API pública~\cite{obrien2022strangler}. No son problemas aislados. Una revisión de 85 estudios agrupa los desafíos de los microservicios en nueve categorías, entre ellas seguridad y monitorización~\cite{soylemez2022challenges}. Entrevistas a 19 ingenieros de 16 empresas describen la migración como un proceso iterativo, con un cambio sistémico y otro técnico~\cite{ayas2023empirical}.

\section{Aplicación al proyecto propio}

El SSDC parte de una aplicación web existente y su PFC será de microservicios. De SoundCloud tomo tres decisiones. Primera, no añadir funciones al código original: las nuevas nacen como servicios~\cite{calcado2014monolith}. Segunda, los servicios no leen la base de datos del código original y usan su API~\cite{calcado2014monolith}. Tercera, definir desde el inicio qué significa «terminado» y medir el avance~\cite{stuart2016monolith}. No tomo el Strangler ni el BFF en Scala. Resolvieron una API con miles de clientes externos, que el SSDC no tiene. Tampoco una migración de ocho años~\cite{obrien2022strangler}. Para decidir qué extraer primero, Fritzsch et al. proponen una metodología orientada a calidad para descomponer monolitos, apoyada en 110 publicaciones~\cite{fritzsch2026framework}.

\subsection*{Sistema conocido de primera mano}

Ejecuté en mi computador la demo OpenTelemetry Astronomy Shop, una tienda en línea de ejemplo hecha con microservicios, con Docker Compose (\texttt{docker compose up --no-build}). La figura muestra 20 contenedores en ejecución. Cada servicio, como \texttt{cart}, \texttt{checkout}, \texttt{payment}, \texttt{shipping} y \texttt{product-catalog}, corre en su propio contenedor y publica su propio puerto. Los datos viven en contenedores aparte, como \texttt{astronomy-db} y \texttt{valkey-cart}.
